# Reconnect Reset Contract

D04 の実装済み契約。公開 API は `reset_reading_state()`。
現行の所有者と寿命は [Reading State Ownership](reading-state.md) を参照。

## Decision

再接続や利用者が意図して行う読み取り位置の変更に対して、azarashi の抽出状態だけを
明示的に破棄できる小さな操作を採用した。公開 Reader の導入は引き続き保留する。

呼び出し形は `reset_reading_state(stream, msg_type='nmea') -> None`。
`msg_type` は `decode_stream()` と同じ StreamFormat とし、
対象の読み取り元を解決するために使う。消去する保存領域を形式一つに限定する指定ではない。
重複履歴の削除、I/O の開閉、読み取りの中断はこの操作に含めない。

| 方法 | 判断 |
|---|---|
| EOF・タイムアウトで自動的に全消去 | 採用しない。部分読みの再開と矛盾する |
| close/open の自動検出 | 一般のストリームでは観測できない。保証の根拠にしない |
| 毎回別の stream オブジェクトを作る | 抽出状態を分離できるが重複履歴も別になる。既存の選択肢として残す |
| 抽出状態の明示的リセット | 採用。既存の読み取り API と組み合わせる |
| 公開 Reader に再接続と停止を集約 | 並行読み取りの中断・待機も必要になったときに再検討 |

## Scope

| 状態 | リセット時の扱い | 理由 |
|---|---|---|
| 行の読みかけ | 破棄 | 別の接続のデータと結合させない |
| NMEA の抽出済み未配信文 | 破棄 | 完全な文でも以前の接続からの未配信データである |
| UBX の部分フレーム・先読みデータ | 破棄 | 新しい読み取り開始位置から再開する |
| 通知済みの重複履歴・受信時刻 | 保持。時刻の更新もしない | 再接続だけを理由に既報を再通知しない |
| 通知中の予約 | 操作しない | 実行中の通知を取り消す操作ではない |
| stream のロック・抽出用ロック | 同じものを維持 | 待機者と別のロックを作ってしまわない |
| OS・デバイス・Python I/O 内部の受信バッファ | 操作しない | azarashi がまだ読んでいないデータの管理は I/O 側の責務 |
| 南海トラフ情報の組み立て状態 | 操作しない | stream 単位の抽出状態ではない |

履歴の保持は既存の弱参照・閉鎖時の解放条件に従う。失われた履歴を復元するものではなく、
弱参照できない所有者の再接続時の保持保証を広げない。記憶の容量・秒数による通知条件も変えない。

## Shared Owners

対象は `decode_stream(stream, msg_type)` が選ぶ reader の実際の所有者。
束縛メソッドでなければ callable 自体を対象にする。
対象所有者について、部分行・未配信 NMEA 文・UBX バッファの全てを消去する。
`read` と `read1` のようなメソッド名ごとの状態も全て消去する。

`.buffer.read1` が選ばれる場合は内側の buffer が対象となる。
同じ buffer を使う他のラッパーにも消去が及ぶが、各ラッパーの通知履歴には触れない。
外側と内側を辿って無関係な状態まで再帰的に消去しない。

メソッドや形式を切り替える場合、まず旧経路を指定してリセットする。
新旧で実際の所有者が異なるなら、新経路に以前の状態が存在し得るため新経路もリセットする。
`.buffer` や callable 自体を差し替える場合は、差し替える前に旧対象を処理する。
新しい対象から以前の所有者を逆引きする仕組みは追加しない。
リセットは I/O 内部の先読みを戻さないため、メソッドや形式を切り替えても欠落なく
続けられる保証ではない。開始位置の確保は呼び出し側が行う。

## Concurrency and Ordering

初期のサポート範囲は、同じ読み取り元を使う全呼び出しと通知が終了した状態。
読み取り元を共有する他のラッパーも停止対象に含む。
`decode_stream(callback=...)` は通知後に読み続けるため、コールバックが一度戻るだけでは停止にならない。
コールバックの中から自分の読み取りをリセットする使い方も初期の対象外とする。

抽出用ロックだけを取っても、既に抽出を終えてデコード・通知へ進んだ電文は取り消せない。
実行中の通知が後から履歴を更新することもある。したがって「リセット完了後は以前の接続から
何も通知されない」を並行利用中に保証するには、世代番号だけでなく通知の待機・停止契約が必要になる。
今回その仕組みまでは追加しない。実行中の呼び出しがないことの自動検出も保証しない。

実装時は既存と同じ順序（stream のロック → 抽出用ロック）で操作する。
ロックは内部辞書の更新を守るものであり、読み取りの中断やデバイス再接続全体の排他を代行しない。

利用者が切断例外を観測せずに再接続する場合の手順:

1. 同じ読み取り元を使う読み取り処理を停止し、通知も含めて終了を待つ。
2. 旧経路を指定して抽出状態をリセットする。
3. I/O を close/open する。必要なデバイス側の受信バッファ処理も利用者が行う。
4. 読み取りを再開する。既存の重複履歴を引き続き使う。

手順1の停止方法はアプリケーションと I/O に依存する。リセットがブロッキング read を
中断することは約束しない。単一スレッドで1電文ずつ読む場合は、前の呼び出しが戻った後に操作できる。

既存の `AzarashiReopenStream` 捕捉後の再接続例は維持する。
例外経路では、その読み取りで使った部分行・UBX バッファは既に破棄される。
通常の受信タイムアウトではリセットせず、読みかけを残して次の呼び出しで続きを読む。

## Implementation and Acceptance

内部の所有者単位の破棄を実装し、公開操作へ接続した。

- `ReaderStore` に、指定した所有者の項目だけを破棄する操作を設ける。
  他の所有者を走査・解放せず、未登録なら何もしない。抽出データを新たに作らない。
  排他用のロックは必要に応じて生成し、同じ所有者で使い続ける。
- 部分行・NMEA・UBX の保存領域に同じ対象を適用する。
  全体の `clear()` や、ロック辞書の削除で代用しない。
- reader の選択処理を `decode_stream()` と共有する。失敗時は消去を始めず、
  未対応形式・読み取りメソッド不足の扱いを既存 API と一致させる。
- 公開時は型、API 文書、公開名の互換テストと型検査も更新する。

受入条件（回帰テストで確認）:

| ケース | 期待する結果 |
|---|---|
| 部分 NMEA/HEX 行、部分 UBX フレームが残った状態 | 旧データを結合せず、新しい完全な電文を読める |
| 完全な未配信 NMEA 文・先読みした UBX 電文が残った状態 | リセット後には返らない |
| 既報の電文が再接続後に再び届く | 同じ stream の既存の重複条件に従って抑制する |
| 二つのラッパーが同じ buffer を共有 | 未配信データは両方から消え、通知履歴はそれぞれ保持する |
| 独立した読み取り元 | 状態に影響しない |
| 同じ所有者の複数メソッド | 対象所有者の各保存領域が消える |
| 未使用・既にリセット済みの対象 | 繰り返しても問題なく、状態を新規生成しない |
| GC・弱参照不可の対象 | 新たな強参照を残さず、既存の保持制約を悪化させない |
| I/O 内部にだけ残るデータ | リセットで read・seek・flush・close を呼ばず、消去しない |

この操作は状態の内容を捨てるもので、強参照で保持した全管理情報の解放 API ではない。
弱参照不可な対象の全管理情報を解放する API は今回は追加しない。共有元の利用終了を
把握しないままロックを削除すると、既存利用者と新規利用者で排他が分かれるため。
この制約が問題になる用途では弱参照可能なラッパーを使い、明示的ライフサイクル API は
読み取りの停止・所有者の管理を併せて設計するときに扱う。
