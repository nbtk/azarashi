# Reading State Ownership

2026-09-21、D04 の調査。現行実装の記録と設計判断であり、未対応の使い方を新たに保証する文書ではない。

## Owners

| 状態 | 保存場所 | 識別する所有者 | 値から所有者への参照 |
|---|---|---|---|
| 重複履歴（最大256件） | `api.caches` | `decode_stream(stream)` の `stream` | 通常のレポートにはない |
| 通知中の予約 | `api.deliveries` | 同上 | 通常のレポートにはない |
| 読み取り・状態更新用 RLock | `state._locks` | 同上 | ない |
| 行の読みかけ | `state._partial_lines` | `reader.__self__` と `reader.__name__` | 文字列・バイト列だけ |
| NMEA の行から抽出した未配信の文 | `nmea._pending_sentences` | 同上 | 文字列だけ |
| UBX の読みかけ・先読みした未配信バイト列 | `ublox.buffers` | 同上 | バイト列だけ |

下3行は `ReaderStore` を使用する。束縛メソッド以外は callable 自体を `_unowned` の
キーとし、オブジェクト同一性で識別する。弱参照可能なら回収とともに状態を解放し、
弱参照できなければ強参照する。同じ所有者でも `read` と `read1` は別の状態になる。
`reader_args` はキーに含まれない。

参照元: [API](../../azarashi/api.py)、[状態管理](../../azarashi/streams/state.py)、
[NMEA](../../azarashi/streams/nmea.py)、[UBX](../../azarashi/streams/ublox.py)。

## Lifetime

以下は弱参照できる所有者の場合。タイムアウトは pySerial 型の空読み・部分読みを指す。
ソケットの `TimeoutError` は読み取り失敗として `AzarashiReopenStream` に変換する。

| 状態 | タイムアウト | EOF | 読み取りで切断・閉鎖を検出 | 同じ所有者の close/open | 所有者の GC |
|---|---|---|---|---|---|
| 重複履歴 | 保持 | 保持 | 保持 | 保持 | 解放 |
| 通知中の予約 | 他の呼び出しの予約は保持 | 同左 | 同左 | close/open では解除しない | 解放。ただし実行中の呼び出しは stream を保持 |
| ロック | 保持 | 保持 | 保持 | 保持 | 解放 |
| 行の読みかけ | 保持。計1024を超えると破棄 | EOF 分岐自体は消去しない | その reader の読みかけを消去 | 操作自体では消去しない | 解放 |
| NMEA の未配信文 | 読み取り前に未配信文を先に返す | 同左 | 同左 | 残っていれば返す | 解放 |
| UBX バッファ | 消費途中のヘッダ等も戻して保持 | 同左 | その reader のバッファを消去 | 操作自体では消去しない | 解放 |

通常、行の EOF は timeout のない reader の空読みであり、読みかけは生じない。
途中で timeout を変更すると、以前の部分行が EOF 後にも残る場合がある。
EOF は状態のリセットではない。seek による再生でも同じ所有者の重複履歴が残る。

通知予約は `unique` 使用時にロック内で登録する。コールバックはロック外で実行し、
成功時に履歴を確定して予約を解除する。失敗時は予約だけを解除する。
他の呼び出しが通知中に読み飛ばしたコピーを再配信する仕組みはない。
`unique=False` の呼び出しは既存の履歴・予約を消去しない。

弱参照できない所有者は、各辞書が別々に強参照する。`get()` が弱参照の既存項目を
返さず、強参照側を検索する際に `closed=True` の項目を掃除する。
閉じた瞬間に全辞書から解放する仕組みではなく、各辞書の検索時期にも依存する。
弱参照できず `closed` もない所有者・callable は自動解放されず、内部の `clear()`
またはプロセス終了まで残る。公開 API に個別解放の操作はない。

## Findings and Decision

**今はすべてを一つの状態オブジェクトにまとめない。** 所有者と寿命の違いを隠してしまうため。
次の二層に分ける方向が適切と判断する。

- API に渡す stream ごとの通知状態（重複履歴・通知予約・その更新を守るロック）。
- 実際の読み取り元ごとの抽出状態（部分行・未配信文・UBX バッファと読み取りの排他制御）。

現行のロックは両方を守るが、次の場合は所有者が一致しない。まず契約と排他範囲を
確定し、その後に集約する。新しい状態に stream や束縛メソッドを強参照で保存すると、
弱参照のキーを値側から生かし続けるため、集約時も保存しない。
レポートは変更可能なので、利用者が属性に stream を追加する場合まで GC を保証できるわけではない。

### Shared Reader

UBX の `.buffer.read1` を使う場合、通知状態は外側のラッパーに、バッファは内側に属する。
同じ内側を二つのラッパーから使うと、未配信バイト列は共有するが、ロックと重複履歴は別になる。
逐次利用でこの違いを再現した。並行利用の競合結果は今回検証していない。
外側の GC は内側が所有するバッファを消去しない。

次の検討では、共有読み取り元の並行利用をサポートするかを決める。
サポートする場合は読み取り元側の排他制御が必要。通知履歴まで内側に移すと
別ラッパー間の重複抑制が変わるため、同時に移さない。

### Release and Reconnect

当初の調査では、束縛されていない関数は最後の利用者参照を捨てても残り、
`clear()` 後に回収された。この保持は `StreamKeyedDict` の利用で修正した。
関数を使っている間は未配信文を保持し、利用終了後は、関数がクロージャで参照する
ストリームも回収できることを回帰テストで確認する。値には reader を保存しない。
等価な callable も同一性で分離し、ハッシュ不能な callable も受け入れる。

弱参照できない callable は強参照で保持する。`closed=True` を後の検索で確認すると解放するが、
`closed` のないものには自動解放の手掛かりがない。この場合の明示的解放の契約は引き続き検討する。

読みかけを持つ同一オブジェクトを、例外を検出する前に close/open すると読みかけは残る。
前の接続の部分行と再接続後の末尾から一文を完成できることを自作 reader で確認した。
また、閉じた NMEA ストリームからも、既に抽出した次の文は読み取りなしで返る。
「切断時に全未読データを破棄する」とは約束できない。

外部の close/open を常に検知することはできないので、将来の明示的な再接続通知や
リセット操作では、抽出状態だけを捨て、重複履歴を残す契約を候補にする。
公開 Reader の追加を今決める根拠にはせず、既存 API と直接 extractor を呼ぶ経路も含めて検討する。

## Evidence

既存の `test_stream.py`、`test_interface.py`、`test_timeout.py`、`test_ublox.py` の
計87テストが成功。通知失敗、並行読込、所有者の回収、部分読みの再開を含む。
`test_disconnect.py` の再接続テストは、例外を観測した後に読みかけを破棄する経路を検証している。

上記の共有 buffer、関数の保持、例外を観測しない close/open、閉鎖後の未配信文は
一時的な確認コードで再現した。現行の制約を将来も守る回帰テストにはしていない。
EOF・再接続・解放の望ましい契約を決めた後、その契約を確認するテストを追加する。

関数 reader の解放修正では、クロージャの回収テストが修正前に失敗することを確認した。
未配信文の保持、等価でハッシュ不能な callable の分離、factory が `None` を返す場合も検証する。
